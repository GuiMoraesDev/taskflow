# Scope — <Short Title>

One line: what this work addresses and why it is needed now.

---

## In scope

The areas this plan may change. Name them as paths or subsystems, not as themes -
"the checkout total calculation in `src/cart/`" rather than "pricing".

---

## Out of scope

The areas it must not touch. Be specific about the **tempting** ones - the
adjacent mess that any honest reader of the code will want to fix on the way
past. An out-of-scope list that only names things nobody would have done anyway
is doing no work.

**Escape hatch:** if a task turns out to require one of these, stop and raise it
rather than widening the plan. Widening silently is the failure this file exists
to prevent.

---

## Constraints

Anything fixed that the tasks have to plan around: a release date, a schema that
cannot migrate yet, an API whose consumers are not ours, a dependency pinned for
a reason. Say what it constrains, not just that it exists.

---

## Definition of done

What has to be true for this plan to be finished, in terms a reader can check
without reading `TASKS.md`.
